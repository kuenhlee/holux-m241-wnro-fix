## 環境

- macOS 26.3 (Apple Silicon)
- ドライバ: Apple 標準 CP210x VCP（追加インストール不要だった）
- デバイスノード: `/dev/tty.usbserial-0001`

## チップ識別 (PMTK605 応答)

```
$PMTK705,B-core_1.20,0043,01017-00F,1.0*72
```

| フィールド | 値 | 解釈 |
|----------|----|------|
| Release | `B-core_1.20` | MTK 旧世代ファーム命名（MT3318 系） |
| Build | `0043` | 内部ビルド番号 |
| Product Model | `01017-00F` | Holux 製品識別 |
| SDK ver. | `1.0` | |

→ **チップ = MT3318 確定**（Holux 公式仕様とも一致）

## 観測されたデバッグ文字列

NMEA 出力に混じって以下のような文字列が現れた（おそらくユーザーがボタン操作中）:

```
======Setting_ProcessKeys========
======Setting_Destructor========
======ShowTLog_Constructor========
```

C++ オブジェクトのライフサイクル風 → **表示制御 MCU が同じ UART に乗っていて、キー操作時に自分のデバッグ出力を吐いている**と推定。

### このことの含意

- MT3318 と表示 MCU は UART を共有（少なくとも TX 線）
- PMTK は MT3318 に届き、応答も Host に返ってきている → Boot ROM プロトコルも素直に使える期待
- 表示の日時表現は MT3318 が出す NMEA RMC をそのままパースしてるだけと思われる → **MT3318 ファーム単独パッチで OLED 表示も治る**仮説を維持
- リスク: Boot ROM モードに入ると NMEA が止まり、表示 MCU が異常状態になる可能性あり（電源 OFF/ON で復帰する想定）

## ファームバージョン表示

端末本体 Setting メニューの「Version」表示: **V1.13**（GPS チップの `B-core_1.20` と不一致）。

→ **2チップ構成が確定**: MT3318 と表示 MCU は別ファームを持つ
→ Holux 公式 Utility が更新していたのは表示 MCU 側（v1.11/1.12/1.13）。**MT3318 ファームは公式アップデート対象外** だったため、Holux は WNRO を直せなかった or 直す気がなかった
→ 我々の Boot ROM 直接アクセス経由のパッチは、Holux のアップデート機構を介さないので、表示 MCU 側に影響を与えずに MT3318 だけを書き換えられる（仮説）

### 操作時のデバッグ文字列

ユーザーが Setting メニューを操作中に出現:

```
======Setting_ProcessKeys========
======Setting_Destructor========
======ShowTLog_Constructor========
```

→ 表示 MCU が C++ 風コードでデバッグ出力を同じ UART に流している。仕様外動作だが解析の手がかりにはなる（クラス名やライフサイクルが見える）。
